## 一、项目概述

《暗渊回廊》是一款**纯浏览器运行的回合制 Roguelike 地牢游戏**。玩家扮演下潜者，逐层深入 15 层程序化生成的地牢，在每层选择祝福强化自身，击败三个 Boss，最终屠龙通关；通关后可进入无尽回廊或挑战十阶「深渊契约」。

**技术定位**：一个**零第三方运行依赖、零素材文件、零联网请求**的完整可玩游戏。全部美术由 Canvas 2D 程序化绘制，全部音效由 WebAudio 实时合成，唯一外部资源是一份 OFL 开源协议的像素字体（可自由分发）。

| 指标 | 数值 |
|---|---|
| 单文件版体积 | 353 KB（HTML + JS + CSS 全内联） |
| 游戏代码量 | 8,369 行原生 JavaScript（20 个模块） |
| 自动化测试 | 992 行 headless 仿真测试 |
| 版本迭代 | 14 次提交，6 个大版本（v2.0.0 → v2.5.0） |
| 渲染性能 | 常见帧耗时 0.1 ms（GC 治理前 2.9 ms） |
| 运行环境 | 任意现代浏览器；`file://` 双击即玩，无需服务器 |

## 二、AI 工具应用说明

### 2.1 使用的 AI 工具

| 工具 | 用途 |
|---|---|
| **ZCode 智能编程助手** | 主开发环境，承担需求拆解、架构设计、代码生成、测试编写、文档撰写 |
| **GLM-5.3** | 主力模型：模块化代码生成、重构、调试 |
| **DeepSeek V4.1** | 协作模型：交叉评审、方案对比、疑难排查 |

**双模型协作方式**：同一份代码由两个模型先后审阅，交叉发现对方遗漏的问题（例如渲染器性能治理方案由一方提出、另一方验证边界情况）。这相当于给 AI 输出加了一层"代码评审"。

### 2.2 AI 辅助代码占比

本项目的**代码实现几乎全部由 AI 生成**，人工承担的是**决策与验收**。具体拆分：

| 环节 | 主体 | 说明 |
|---|---|---|
| 创意方向 / 玩法设计 | **人工** | 核心循环、职业设定、共鸣系统、深渊契约等设计决策 |
| 架构设计 | AI 起草 + 人工确认 | 模块划分（20 个模块）、全局命名空间、加载顺序 |
| 代码编写 | **AI 生成** | 约 95% 的代码由 AI 产出，人工做小范围修正 |
| 自动化测试 | **AI 生成** | 992 行仿真测试由 AI 编写并持续维护 |
| 数值平衡 | AI 扫描 + 人工定档 | AI 跑网格搜索输出胜率曲线，人工决定最终数值 |
| 美术风格 | **人工定调** | 像素风方向、配色方案由人工决定，像素位图由 AI 绘制 |
| 验收测试 | **人工** | 实际游玩并判断"是否好玩"，这是 AI 无法替代的环节 |

### 2.3 AI 协作开发流程

```
需求拆解 → 代码生成 → 自动化测试 → 浏览器实测 → 真实玩家反馈 → 下一轮
```

1. **需求拆解**：把"做个游戏"拆成可验证的任务清单（如"实现 FOV"、"实现伏击房"）。
2. **代码生成**：按模块生成，遵守"零依赖"硬约束（禁止引入任何 npm 包）。
3. **自动化测试**：`node tools/smoke.js` 跑 headless 仿真，覆盖地图连通性、FOV、战斗采样、整局 bot 通关、存档往返。
4. **浏览器实测**：启动本地服务器，用浏览器自动化真实渲染、截图、点击验证。
5. **真实反馈**：同学/玩家试玩 → 反馈 → 形成下一轮需求。

### 2.4 AI 协作的实际价值（可验证案例）

AI 不只是"写代码更快"，而是**能发现真人难以察觉的缺陷**。以下三个 bug 均由自动化测试或 AI 交叉审查发现：

| 缺陷 | 症状 | 如何发现 |
|---|---|---|
| **伏击房死局** | 玩家触发伏击后可走出结界却再无法进入，房间永久无法清除，表现为"顶怪不掉血、自己却掉血" | 玩家反馈 + AI 定位到边界判定逻辑缺陷，整体重做为"结界边界规则" |
| **新增设施堵死通路** | 铁匠台可能封死出生点到楼梯的唯一路径 | 回归测试 `SMOKE-B F19` 断言"楼梯不可达"失败 |
| **祝福 flag 从未生效** | 10 余种祝福的属性加成生效，但触发类效果（荆棘/汲血/法泉等）全部失效 | AI 交叉审查发现 `Object.assign` 漏合并 `bb.flag` |

此外，**渲染器 GC 治理**使常见帧耗时从 2.9 ms 降至 0.1 ms（200 帧探针，p99 从 54 ms 降至 10.7 ms）——这是 AI 提出方案、人工验收的典型案例。

### 2.5 人工不可替代的部分

必须诚实说明：**AI 能写出能跑的代码，但判断不了"好不好玩"**。

- 玩家反馈"太晃眼睛"→ 人工决定改为固定镜头（AI 不会主动提这个）
- 玩家反馈"装饰太 low"→ 人工决定引入像素字体 + 重制 UI
- 玩法是否够深、祝福是否平衡 → 必须真人试玩判断
- 是否保留某个"不完美但有趣"的设计 → 人的品味

## 三、技术架构

### 3.1 整体分层

游戏按职责分为五层，自顶向下：

**入口层** — `index.html` · 覆盖层 UI · 像素风 CSS

**数据层** — `config` / `tiles` / `sprites` / `items` / `enemies` / `boons` / `story` / `talents`（纯数据表，无逻辑）

**系统层** — `mapgen`（地图生成）· `fov`（视野）· `pathing`（寻路）· `combat`（战斗结算）· `status`（状态效果）· `ai`（敌人行为）· `save`（存档）· `meta`（成就与图鉴）

**表现层** — `render`（Canvas 渲染）· `particles`（粒子）· `audio`（WebAudio 合成）· `hud`（侧栏）

**主控层** — `main.js`：回合引擎 / 输入处理 / 状态机

**关键约束与取舍**：

- **不用 ES Module**：使用全局命名空间 + `<script>` 按依赖顺序加载。原因：`file://` 协议下 ES Module 会被 CORS 拦截，而"双击即玩"是本项目的核心体验承诺。
- **无构建步骤**：没有 webpack/vite，源码即产物。降低协作门槛，也让评审可以直接读源码。
- **单一状态源**：`Game` 对象持有全部运行时状态，存档即序列化该对象的核心字段。

### 3.2 核心模块实现逻辑

#### ① 回合引擎（`main.js`）

一回合的完整流程：

```
玩家输入 → 玩家动作结算 → 敌人 AI 行动 → 状态效果 tick → FOV 重算 → HUD 刷新
```

- **输入**：键盘事件映射为动作（移动/攻击/技能/防守/交互）。
- **结算**：`afterAction()` 统一推进回合数、执行敌人行动、触发状态效果、检查死亡。
- **敌人行动**：按 `speed` 累积器决定行动次数（0.5 = 隔回合动，2 = 一回合两动）。
- **视野**：每回合重算 FOV（递归阴影投射，8 象限 OCT 变换）。

#### ② 地图生成（`mapgen.js`）

三种生成器按楼层切换：

| 类型 | 算法 | 适用 |
|---|---|---|
| `rooms` | 随机散布矩形房间 → 最近邻连接走廊 + 随机开门 | 标准层 |
| `cave` | 细胞自动机（5 次迭代）→ 只保留最大连通区域 | 洞穴层 |
| `arena` | 中央大房间 + 周边小房间 + 走廊 | Boss 层 |

**连通性保障**：生成后 BFS 检查出生点→楼梯可达；不可达则依次尝试清除碎石、打开宝箱、直线强拆。`ensureConnectivity()` 是防止软锁的最后一道防线（铁匠台堵路 bug 就是靠它兜底 + 测试断言发现的）。

**确定性**：所有随机数来自 `RNG.derive(seed, 'map' + floor)`，同一 seed + 同一层必产出同一张地图——这是"每日挑战"（全世界同一天同一张地牢）的技术基础。

#### ③ 战斗系统（`combat.js`）

伤害公式：

```
伤害 = max(1, round(攻击 × 浮动(±20%) × 暴击倍率 × 各类增伤 - 有效防御))
命中率 = clamp(命中 - 敌人闪避, 15%, 95%)
```

**挂钩机制**：所有词条/祝福/挑战因子通过玩家的 `flags` 对象统一挂钩，避免在战斗逻辑里写大量 `if`。例如：

```javascript
if (f.pierce) effDef *= 0.5;                    // 破甲
if (f.execDmg && hp/maxHp < 0.3) dmg *= 1.5;   // 处决者
if (f.bossDmgMul && enemy.boss) dmg *= ...;    // 破军
```

**战术姿态（v2.5）**：按 E 防守 → 本回合受伤 ×0.45，回合末转为 `guardCharge` → 下次攻击 ×1.6。这让"对撞"不再是唯一动词。

#### ④ 视野系统（`fov.js`）

递归阴影投射（Recursive Shadowcasting），8 个象限各 8 个八分仪。相比射线法，它不会有"透过墙角看到背面"的伪影，且复杂度为 O(可见格数)。

#### ⑤ 渲染系统（`render.js`）

**性能设计**（GC 治理的核心）：

| 层 | 策略 |
|---|---|
| 静态层（地砖 + 光照 + 迷雾） | 离屏 Canvas 缓存，仅在楼层/回合/地砖变化时重绘 |
| 光晕 | 预渲染为精灵，每帧 `drawImage` 而非 `createRadialGradient` |
| 暗度着色 | 字符串查表（0~34 档） |
| 实体 | 像素精灵离屏缓存，`imageSmoothingEnabled = false` 保持硬像素 |

**结果**：常见帧 2.9 ms → 0.1 ms，p99 54 ms → 10.7 ms。

#### ⑥ 像素精灵系统（`sprites.js`，v2.4）

每个精灵是一个 **8×8 字符位图** + 调色板：

```javascript
rat: {
  pal: { g: '#9c8472', p: '#e8a0a0' },
  map: [
    '.o....o.',   // o = 描边, g = 身体, p = 鼻子
    'opo..opo',
    'oggggggo',
    'ogegggeo',   // e = 眼睛
    ...
  ],
}
```

运行时首次使用时渲染到离屏 Canvas（放大 3 倍 = 24px 一格），之后直接 `drawImage`。零图片文件，且改一个字符就能调整造型。

#### ⑦ 存档系统（`save.js`）

单存档槽，序列化为 JSON 存入 `localStorage`，**死亡即删档**（Roguelike 铁律）。

只存纯数据，关卡对象在读取时重建。兼容性设计：`v2` 格式兼容读取 `v1` 存档；`recalcStats()` 对 `NaN`/`null` 做防御性修复（防止旧存档导致属性变 NaN）。

#### ⑧ 祝福共鸣（`boons.js`，v2.4）

每张祝福带 `tag` 标签（`war` / `magic` / `survival`），`bonus()` 汇总时统计各 tag 的**不同祝福种类数**，达到 3 种即激活对应共鸣：

```javascript
activeResonances(p) {
  const counts = {};
  for (const id in p.boons) if (BOONS[id].tag) counts[BOONS[id].tag]++;
  return Object.keys(counts).filter(t => counts[t] >= 3);
}
```

这解决了"祝福都是散装增益、缺少构筑感"的设计问题——玩家必须专精才能吃到额外收益。

## 四、质量标准

### 4.1 自动化测试

文件：`tools/smoke.js` + `tools/sim-body.js`（992 行）

| 测试段 | 覆盖内容 |
|---|---|
| 1. 地图生成 | 2 seeds × 20 层：楼梯可达、出生点可走、敌人不在墙里、物品位置合法 |
| 2. FOV | 30 张地图：出生点自身可见、可见格数下限 |
| 3. 战斗采样 | 13 种敌人 × 300 场 1v1：胜率/余血/回合数 |
| 4. 整局 bot | 5 seeds 自动游玩：能否通关、每层血量曲线 |
| 5. 存档往返 | 存读一致性（tiles/enemies/背包/坐标） |
| 6+. 系统用例 | 词条/祝福/天赋/精英/伏击/职业/词缀/碎片/共鸣/契约/商店 |

### 4.2 数值平衡

文件：`tools/balance.js`（网格搜索）

对敌人数值做参数扫描，输出不同档位下的胜率与余血曲线，据此定档（如 Boss 血量 165/430/700 就是网格搜索的甜点区）。

### 4.3 浏览器实测

每次发版前用浏览器自动化做真实渲染验证：截图检查视觉、点击检查交互、读取 `window.__errors` 确认为空。
